### 1-2. このプロジェクトで大切にしている考え方

- **遊びやすさを最優先する**：見た目の華やかさより先に、操作の分かりやすさ・押しやすさ・情報の伝わりやすさを優先する（例：センターなしの表示、収録曲一覧のタップ領域、スマホでの折り返し対応など）。
- **拡張しやすい設計を維持する**：曲を増やす・画面を増やす・選択肢を増やすといった将来の変更が、既存コードへの大きな手直しなしで行えることを常に意識する（`songs.js`への追加だけで完結する曲データ、`SCREEN_ELEMENTS`への1行追加で済む画面追加など）。
- **著作権への配慮を最優先する**：本物の音源・関連データの扱いは、常に「合法かどうか」を先に検討し、少しでも怪しい方法は提案しない（2章参照）。
- **実装前に必ず設計確認を行う**：「設計提案 → 本人の了承 → 実装」という順番を守り、仕様が固まっていない機能は実装から始めない（15章参照）。

## 2. 著作権に関する方針（最重要・繰り返し確認済み）

- 本物の＝LOVE楽曲の音源は、**著作権保護のためGitHubには絶対に公開しない**。
- 音源ファイルは`assets/audio/local/`にのみ配置し、`.gitignore`で除外済み。
- コード（HTML/CSS/JS）自体はいつでも公開できる状態を維持する。

### 画面ごとの演出強度（意図的に差をつけている）
- **スタート画面・結果画面**：演出は華やかめ。背景装飾（ギンガムチェック模様・光の玉・ぼかしたレコード盤・キラキラの粒）をしっかり効かせる。
- **クイズ画面**：「プレイ中に一番長く見る画面」という理由で、背景演出を意図的に控えめにしている。実装は`body[data-screen="quiz"]`でCSS変数（`--pattern-opacity`等）を上書きする方式（`js/screens.js`の`showScreen()`が`body`の`data-screen`属性を更新）。カードのガラスの透け感も弱め、文字のコントラストを優先。

## 5. 採用している設計・アーキテクチャ

- **フレームワーク不使用**。素のHTML/CSS/JavaScript（ES Modules）。
- 状態管理は`state.js`の`gameState`という1つのオブジェクトに集約し、**変更は必ず`state.js`の関数経由で行う**というルール。
- 各JSファイルは役割ごとに分割されており、`import`/`export`で繋いでいる（一覧は6章）。
- コードコメントは日本語。「何をしているか」だけでなく「なぜそうしているか」を書く方針。
- 曲データ（`songs.js`）とゲームロジックは完全に分離。曲を増やす作業は`songs.js`を編集するだけで完結する。
- CSSの色・間隔・アニメーション速度などはCSS変数（`:root`）に集約。新しい画面固有の調整は`body[data-screen="..."]`でのCSS変数上書きというパターンを使う（クイズ画面の演出を控えめにする際に確立した手法）。
- **拡張しやすさを見越した設計判断（すでに実施済み）**
  - 画面の追加（曲一覧画面など）は、`js/screens.js`の`SCREEN_ELEMENTS`という対応表に1行足すだけで済む。
  - 出題数のラジオボタンも、`index.html`に`<label>`を1つ増やすだけで選択肢を増減できる（2026-07-28以降は`.option-row`という入れ物2つに分けているため、増やす際はどちらの段に入れるかも決める。詳細は9章・10-4章）。
  - 結果画面のランクバッジ（`.rank-badge`）は、称号・コメントを追加したくなったら中に要素を1つ足すだけで済む構造。
  - 出題数・カテゴリを指定してクイズを開始する処理は`js/main.js`の`beginQuiz()`に共通化済み（10章参照）。
- **ES Modules撤廃（方法A）は、今後の機能追加フェーズも含めて全体がほぼ完成した最後に行う方針で確定済み**。理由：機能追加の途中でモジュール構成を変えると、実装・管理がかえって複雑になるため（本人の判断）。
  - 手順（着手時の想定）: (1) `<script type="module">`と各ファイルの`import`/`export`を撤廃し、IIFEなどで名前空間を区切った普通の`<script>`構成に書き換える (2) ユニットテストで計算ロジックの回帰がないか確認 (3) Live Serverで通常通り動作確認 (4) スマホの`file://`で直接開いてオフライン動作を確認
  - **実施前に必ずバックアップを取る**（フォルダコピー、またはGitでの記録）。
  - PWA/Service Worker化も検討したが、Service Workerは`https`または`http://localhost`でしか動かないという制約があり、「PCがサーバー・スマホがLAN経由でアクセス」という今の構成とは相性が悪いため不採用と判断済み。

## 9. これまで決めたゲームルール

### スコアリング（`score.js`）
段階式（ティア）方式。出題開始（＝曲が実際に鳴り始めた瞬間）からの経過秒数に応じて、1問10点満点：

| 経過秒数 | 得点 |
|---|---|
| 3秒以内 | 10点 |
| 5秒以内 | 9点 |
| 8秒以内 | 8点 |
| 12秒以内 | 7点 |
| 20秒以内 | 6点 |
| 30秒以内 | 5点 |
| 45秒以内 | 4点 |
| 60秒以内 | 3点 |
| 60秒超 | 2点 |
| 不正解・スキップ・答えを見る | 0点 |

- 制限時間による強制終了は**廃止**。曲は最後まで自動再生され続けるが、曲が終わっても問題自体は終了せず、回答/スキップ/答えを見るのいずれかをプレイヤーが選ぶまで待ち続ける。
- ランクは「1問10点満点 × 出題数」に対する達成率で判定: 90%以上=S、70%以上=A、50%以上=B、それ未満=C。
- **無音の頭出し（`introLeadInSec`）について**：曲の頭に無音区間がある場合（例: 拝啓 貴方様、約4.4秒）、`js/audio.js`が再生開始時にその秒数分シークしてから再生する。これにより無音を聞かせずに済み、`score.js`の採点ロジックはこの値を一切受け取らない（採点tierのルール自体は変更なし）。2026-07-27に「採点時に差し引く」方式から「再生位置を頭出しする」方式に変更した（元の方式だと無音を聞かされる体験自体は解決しなかったため）。

### 回答時間の記録（`state.js`・`main.js`）
- 曲が実際に鳴り始めた瞬間（`playing`イベント）から回答確定までのミリ秒を、`gameState.answerLog`の各要素に`elapsedMs`として記録（丸めていない生の値）。採点には使わず、結果画面の内訳表示（「⏱◯.◯秒」バッジ、表示時だけ小数第1位に丸め）と将来の記録機能のために使う。
- 計測開始点は、再生を試みた直後の暫定値→`playing`イベントで正確な値に上書き、という2段構えにしてあり、超高速回答でも必ずデータが記録される（`markPlaybackStarted()`を2箇所から呼ぶ設計）。

### 出題数の選択肢（`index.html`のラジオボタン、2026-07-28に5段階へ変更）
- 値は`"5"`／`"10"`／`"20"`／`"50"`／`"all"`の5つ。表示は「5問／10問／20問／50問／全曲」。
- スタート画面では、PC幅・スマホ幅どちらでも「5問 10問 20問」「50問 全曲」の3・2配置に固定表示（`.option-row`という入れ物で2段に分けている。詳細は10-4章）。
- `quiz.js`の`resolveQuestionCount(questionCountValue, poolSize)`が、指定した出題数とカテゴリ絞り込み後の曲数（`poolSize`）を比較し、`Math.min(requestedCount, poolSize)`で実際の出題数を決める。例えば「表題曲のみ（22曲）」で「50問」を選んでも、自動的に全22問になる。
- 選んだ出題数が対象曲数を上回るときは、スタート画面に「対象曲数が50曲未満のため、全22問を出題します」という案内をリアルタイムで表示する（`main.js`の`updateQuestionCountNotice()`）。

### カテゴリ絞り込み（`quiz.js`の`filterSongsByCategory`）
- `"title-track"`: 表題曲のみ（22曲）
- `"title-and-group"`: 表題曲＋全員曲（59曲、ユニット曲を除く）
- `"all"`: 絞り込みなし（81曲、ユニット曲・特別収録曲のOvertureも含む全曲）
- 4択クイズを作るには最低4曲必要（`MIN_SONGS_REQUIRED`）。足りない場合はエラーメッセージを表示。
- **表示順・初期選択**（2026-07-28変更）：スタート画面では対象曲数が少ない順に「表題曲のみ→表題曲＋全員曲→全曲」と並べ、**初期選択は「表題曲のみ」**（初めて遊ぶ人が一番遊びやすい範囲から始められるようにする方針）。各選択肢には対象曲数を自動集計して表示する（`main.js`の`updateCategoryCountHints()`）。`value`属性・絞り込みロジック・ハイスコアキーはこの変更による影響を受けない（表示順とチェック状態だけの変更）。

### 4択の選択肢生成（`quiz.js`の`generateChoices`）
- **完全ランダム**。正解の曲以外のプール内の曲からランダムに3つ選び、並び順もシャッフルする。同じ曲が出題されても、毎回ダミー選択肢の組み合わせ・並び順は変わる（固定ペアは存在しない、2026-07-27に本人に確認・回答済み）。

### スキップ／答えを見るの挙動の違い
- **スキップ**: 0点記録、正解は見せずに即座に次の問題（または結果画面）へ
- **答えを見る**: 0点記録、正解の曲名を表示 →「次へ」ボタンで進む（スキップより1テンポ遅い）

### 自己ベスト（`highscore.js`）
- 出題数・カテゴリの**組み合わせごと**に別々のlocalStorageキーで保存（`equalLoveIntroQuiz.highScore.{出題数の値}.{カテゴリの値}`）。同点は新記録扱いにしない（厳密に上回った場合のみ）。
- 出題数に`"20"`／`"50"`が増えた（2026-07-28）際も、`equalLoveIntroQuiz.highScore.20.{category}`／`.50.{category}`という新しいキーが自動的に増えるだけで、既存の`"5"`／`"10"`／`"all"`の記録には一切影響しなかった（保存キーの設計が最初から将来の選択肢追加を見越していたため）。
- 2026-07-27以前は単一キーで全モード共通の値しか保存できておらず、「全曲モードの670点が5問モードでも自己ベストとして表示される」不具合があったため、上記の方式に修正した。この変更に伴い、修正前の単一キーに保存されていた古い記録（670点）は、どのモードのものか判別できないため引き継いでいない（本人に説明・合意済み）。

### 10-1. 結果画面の2ボタン化（2026-07-27実装）

結果画面のボタンを「もう一度挑戦する」（主ボタン）と「タイトルに戻る」（副ボタン）の縦2段構成に分割した。

- **もう一度挑戦する**：直前と同じ出題数・カテゴリを引き継ぎ、**スタート画面を経由せず**、曲順・4択を**再抽選**してそのままクイズ画面を開始する。得点・回答内訳・経過時間・回答済み状態など、今回のプレイに関するものはすべてリセットされる。
- **タイトルに戻る**：出題数・カテゴリの選択も含めて初期状態に戻し、スタート画面で選び直せる状態にする（旧来の「もう一度挑戦する」と同じ動き）。

**実装のポイント**：
- 出題数・カテゴリを指定して曲プールの絞り込み〜クイズ開始までを行う処理を、`js/main.js`の`beginQuiz(questionCountValue, categoryFilterValue)`として共通化。スタートボタンと「もう一度挑戦する」の両方から呼ばれるため、**再挑戦のたびに必ず曲順・4択が再抽選される**（`beginQuiz`内部で`buildQuizQuestions`を毎回呼ぶため）。
- 「もう一度挑戦する」はスタート画面（＝`resetGameState()`）を経由しないため、前回プレイ最後の「回答済み」フラグ（`gameState.isAnswered`）が残ったまま次のゲームに入ってしまうリスクがあった。これを防ぐため、`js/state.js`の`startQuiz()`内で`gameState.isAnswered = false`を確実にリセットするよう修正済み。
- ボタンの見た目：主ボタンは既存の`.primary-button`（ピンク塗りつぶし）、副ボタンは既存の`.secondary-button`（白背景＋ピンク縁取り、スキップ/答えを見るボタンと同じスタイル）をそのまま流用。縦並びは`#result-actions { flex-direction: column; }`で実現し、`.button-row`自体は横並び・縦並びどちらにも使える汎用クラスとして維持している。

## 12. 既知の技術的注意点（再発防止メモ）

### `hidden`属性とCSSの`display`指定が競合するバグ（2026-07-27発見・修正済み）

**症状**: 自己ベストを更新していないのに「🎉新記録！」バッジが表示され続ける不具合が発生。`js/main.js`に一時的な`console.log`を仕込んで調査したところ、判定ロジック（`isNewRecord`）自体は完全に正しく動いていた。原因はJSではなくCSS側だった。

**原因**: HTML標準の`hidden`属性は、本来ブラウザの初期スタイル（`[hidden] { display: none; }`、詳細度が低い）によって非表示になる。しかし`#new-record-badge`にチップ風の見た目を整える際、`display: flex;`をIDセレクタで指定していたため、**詳細度の高いこのCSSが`[hidden]`の`display: none`を上書きしてしまい、JSが`hidden = true`にしても実際には非表示にならない**状態になっていた。同じ原因のバグが`.secondary-button`（スキップ・答えを見るボタン）にも存在し、あわせて修正した。

**修正方法**: `hidden`属性と、`display`を明示的に指定するCSS（`display: flex`など）を同じ要素に使うときは、必ず`セレクタ[hidden] { display: none; }`という上書き用のルールを一緒に用意する。

**今後の注意点**: 新しいUIパーツに`hidden`属性でのJS制御（表示/非表示の切り替え）を組み込む際は、そのパーツのCSSに`display`の指定（`flex`・`grid`・`inline-flex`など、`none`以外の値）があるかどうかを必ず確認し、あれば`[hidden]`用の上書きルールを追加すること。`.primary-button[hidden]`・`#quiz-actions[hidden]`・`#new-record-badge[hidden]`・`.secondary-button[hidden]`・`.modal-overlay[hidden]`にはすでに同様のルールがあり、これがお手本になる。

**追記（2026-07-28、収録曲一覧の試聴ボタンで発見）**: インラインの`<svg>`要素は、`hidden`属性・JSからの`element.hidden = true/false`が反映されない（＝`[hidden] { display: none; }`を上書き用に用意しても効かない）ブラウザがあり、再生/一時停止アイコンが同時に見え続ける不具合が発生した。SVG要素の表示/非表示をJSで切り替えたいときは、`hidden`属性ではなく、**親要素に付け外しするクラス（例: `.track-row.is-playing`）を基点にしたCSSの子孫セレクタだけで見た目を決める**方式にすること。`.track-row.is-playing .icon-play` / `.track-row.is-playing .icon-pause`（`css/style.css`）と、対応する`js/songlist.js`の`setRowPlayingState()`（`classList.toggle()`のみで、アイコン個別への`hidden`操作は行わない）がお手本になる。

### 日本語テキストがflexアイテム内で1文字ずつ折り返されるバグ（2026-07-28、称号チップのスマホ幅表示で発見・修正済み）

**症状**: 結果画面の称号チップ（アイコン・NEWバッジ・称号名・キャプションを横並びにしたピル型UI）が、スマホ幅（375px）で表示すると、称号名が1文字ずつバラバラに折り返されてしまう不具合が発生。「パーフェクト」のような短い文字列でも起きていた。

**原因**: 英語と違い、日本語には単語間のスペースがない。ブラウザは初期設定で、スペースがない言語ではどの文字とどの文字の間でも改行してよいと判断する。横に並べる要素が多く幅が窮屈になりやすいflexレイアウト（`display: flex` / `inline-flex`）の中に日本語テキストを入れると、少しでも幅が足りないと文字単位で折り返されてしまう。

**修正方法**: 改行させたくないテキスト要素に`white-space: nowrap;`を指定する。`.title-event-name`／`.title-event-caption`／`.title-event-badge`／`.title-list-name`（`css/style.css`）で対応済み。

**今後の注意点**: 新しいUIパーツで、横並びのflexレイアウトの中に短い日本語テキスト（ラベル・称号名・ボタン文言など）を入れるときは、スマホ幅で幅が窮屈になった場合に文字単位で折り返されないか、あらかじめ`white-space: nowrap;`を検討すること。ただし、テキストが長くなる可能性がある箇所（説明文など、複数行での折り返しを前提にしている場所）にはむやみに使わないこと（意図的に折り返したい文章まで1行に固定してしまい、画面からはみ出す原因になる）。
