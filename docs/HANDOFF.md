## 4. 採用している設計・考え方

- **フレームワーク不使用**。素のHTML/CSS/JavaScript（ES Modules）。
- 状態管理は`state.js`の`gameState`という1つのオブジェクトに集約し、変更は必ず`state.js`の関数経由で行う、というルール。
- 各JSファイルは役割ごとに分割されており、`import`/`export`で繋いでいる（一覧は5章）。
- コードコメントは日本語。「何をしているか」だけでなく「なぜそうしているか」を書く方針。
- 曲データ（`songs.js`）とゲームロジックは完全に分離。曲を増やす作業は`songs.js`を編集するだけで完結する。

## 6. ファイル命名規則

### 音源ファイル（`assets/audio/local/*.mp3`）
- **ファイル名（拡張子を除く）は、`songs.js`の該当曲の`id`と完全に一致させる**（`js/audio.js`が`` `${AUDIO_BASE_PATH}${song.id}.mp3` ``という形でパスを組み立てているため）。
- `id`はローマ字＋ハイフン区切り、日本語は使わない（URLやGit管理での事故を避けるため）。
- 例: 「＝LOVE」→`love.mp3`、「探せ ダイヤモンドリリー」→`sagase-diamond-lily.mp3`。曲名を省略せずローマ字化するのが基本方針。

### 音源の入手・取り込みフロー（毎回この手順）
1. CDの場合: 外付けBD/DVDドライブ＋Windows Media Player（従来版）で取り込み（形式はMP3、コピー防止は「追加しない」を選択）
2. moraの場合: 「ミュージック」形式ならそのままmp3としてダウンロード。「ビデオ」形式の場合は、まず普通の動画プレーヤーで再生できる（＝コピー保護なし）ことを確認してから、VLCの「メディア→変換/保存」で「Audio - MP3」に変換
3. 取り込んだファイルを、`songs.js`の`id`に合わせてリネーム
4. `assets/audio/local/`に移動

## 7. `songs.js`のデータ構造

```js
export const CATEGORY = {
  TITLE_TRACK: "表題曲",
  GROUP_SONG: "全員曲",
  UNIT_SONG: "ユニット曲",
  SPECIAL: "特別枠",   // Overture専用。「全曲」モードでのみ出現する特別枠
};

export const DIFFICULTY = {
  EASY: "かんたん",
  NORMAL: "ふつう",
  HARD: "むずかしい",
  // 現状、出題ロジックはdifficultyを参照していない（将来の難易度別モード用に先行して持たせている）
};

export const SONGS = [
  {
    id: "love",                 // ファイル名にも使う一意なID（ローマ字）
    title: "＝LOVE",             // クイズの選択肢・正解表示に使う正式な曲名（記号込みの正式表記）
    category: CATEGORY.TITLE_TRACK,
    releaseDate: "2017-09-06",  // "YYYY-MM-DD"形式
    single: "1stシングル「＝LOVE」", // 収録作品名（表示用の補足情報）
    difficulty: DIFFICULTY.EASY,
    introLeadInSec: 0,           // 曲の頭の無音時間（秒）。採点時にelapsedSecから差し引く
  },
  // ...
];
```

- **「アルバム収録」かどうかはcategoryではなく`single`フィールドで表現する。** アルバム曲もシングル曲と同様に「表題曲/全員曲/ユニット曲」のどれかに分類される（＝LOVEの楽曲文化に合わせた分類方式）。
- カテゴリ分類の参考にしているのは、**本人の友人が作成した非公式のまとめ表**（表題曲/全員曲/ユニット曲の一覧）。**この表には実際に誤りがあった**（8thシングルとアルバムのユニット曲を取り違えていた等）。曲の帰属に少しでも疑問があれば、必ずWeb検索で公式情報を確認してから登録すること。
- 曲を追加する際は、この配列に要素を追加するだけでよい（他のロジックへの変更は不要）。

## 8. これまで決めたゲームルール

### スコアリング（`score.js`）
段階式（ティア）方式。出題開始からの経過秒数（`introLeadInSec`を差し引いた後の値）に応じて、1問10点満点：

| 経過秒数（無音補正後） | 得点 |
|---|---|
| 3秒以内 | 10点 |
| 5秒以内 | 9点 |
| 8秒以内 | 8点 |
| 12秒以内 | 7点 |
| 20秒以内 | 6点 |
| 30秒以内 | 5点 |
| 45秒以内 | 4点 |
| 60秒以内 | 3点 |
| 60秒超 | 2点 |
| 不正解・スキップ・答えを見る | 0点 |

- 制限時間による強制終了は**廃止**。曲は最後まで自動再生され続けるが、曲が終わっても問題自体は終了せず、回答/スキップ/答えを見るのいずれかをプレイヤーが選ぶまで待ち続ける。
- ランクは「1問10点満点 × 出題数」に対する達成率で判定: 90%以上=S、70%以上=A、50%以上=B、それ未満=C。

### カテゴリ絞り込み（`quiz.js`の`filterSongsByCategory`）
- `"title-track"`: 表題曲のみ
- `"title-and-group"`: 表題曲＋全員曲（ユニット曲を除く）
- `"all"`: 絞り込みなし（ユニット曲・特別枠のOvertureも含む全曲）
- 4択クイズを作るには最低4曲必要（`MIN_SONGS_REQUIRED`）。足りない場合はエラーメッセージを表示。

### スキップ／答えを見るの挙動の違い
- **スキップ**: 0点記録、正解は見せずに即座に次の問題（または結果画面）へ
- **答えを見る**: 0点記録、正解の曲名を表示 →「次へ」ボタンで進む（スキップより1テンポ遅い）

## 12. 開発の進め方・運用ルール

### 開発ルール（最重要）
- ユーザーはプログラミング初心者。**1ステップずつ、具体的な手順で説明する**のが大原則。開発者ツールの操作（F12、Consoleタブなど）も、毎回迷わず追えるレベルまで具体的に書く。
- **コードを変更する前に、何をどう変えるか説明してから着手する。** 特に、設計に関わる変更（データ構造・ゲームルール・カテゴリ分類の追加など）は、**必ず先に相談し、合意を得てから実装する**。今回の段階式スコアリング導入・カテゴリの3分類化・ES Modules撤廃のタイミング判断は、すべてこの形で合意を取ってから進めた。
- 実装作業では、各ステップが終わるたびに**「変更したファイル／やったこと／確認手順／正常な場合の見え方」を報告**し、ユーザーが明示的に「次へ」と言うまで次のステップに進まない、という報告フォーマットを基本とする。
  - 例外: ユーザーが「もう分かったから細かい説明は省略してほしい」と言った場合（実際に曲データ登録作業の途中でそう言われた）は、その作業に限りテンポよく進めてよい。ただし新しい種類の作業に移るときは、再度ステップバイステップに戻す。
- **大きな設計変更（例: ES Modules撤廃）は、実装のタイミングも含めて必ず相談する。** 今回は「デザイン・機能がほぼ完成してから最後にまとめて行う」という、ユーザー自身の判断（原因切り分けをしやすくするため）を採用した。
- **大きな変更を行う前には、バックアップを取る**（フォルダコピー、またはGitでの記録）。ユーザー自身がこの発想を提案してきたことがあり、今後も同じ姿勢を維持する。
- **著作権については終始慎重に扱ってきた。** 新しい音源入手ルートの提案時は、必ず「合法かどうか」を先に検討し、少しでも怪しい場合（例: 動画ファイルのDRM有無が未確認）は、正直に不確実性を伝える。安全側に倒して、少しでも違法の可能性がある方法（Blu-rayリッピング等）は提案しない。
- 動作確認は基本的にユーザー自身にLive Server経由でブラウザを開いてもらう形。この環境にはNode/Pythonの実体がなく（`python`コマンドはMS Store誘導のスタブ）、自動でローカルサーバーを起動して確認することができない。
- 曲データを新しく登録する際は、**必ずWeb検索で公式情報（発売日・正式な曲名表記・収録内容）を確認してから**`songs.js`に追加する。ユーザーが口頭で伝えてくる曲名は聞き間違い・表記ゆれを含むことがある（例: 「届いてラブ言う」→「届いてLOVE YOU♡」、「背景あなた様」→「拝啓貴方様」）。友人作成の非公式まとめ表も、行のズレなど誤りが実際にあったため、鵜呑みにせず裏取りする。

### Git運用ルール
- コミットは、**動作する状態の、意味のあるまとまりごと**に行う（例: 「1つの機能の実装が完了した」「1バッチ分の曲データ登録が終わった」）。壊れた状態のままコミットしない。
- コミットメッセージは日本語で、**「何を」だけでなく「なぜ」も分かるように書く。**
- 何か一括の作業をする前後で、`git status`で状態を確認する習慣を維持している。
- 作業の区切り（休憩・パソコンを閉じる前など）では、必ず`git status`がクリーンな状態になっているか確認してからコミットする。
