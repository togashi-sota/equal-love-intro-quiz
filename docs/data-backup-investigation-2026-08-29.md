# ユーザーデータの保存・消失リスク・バックアップ設計 調査報告書

作成日: 2026-08-29
調査範囲: `js/` 配下の全モジュール（IndexedDB・localStorage・sessionStorage）、Firebase Realtime Database、関連するadmin/security設計
方針: **本報告書はすべて調査結果であり、まだ一切コードは変更していません**。実装は本人の方針確定後に着手します。

---

## ①現状調査：このアプリのデータ保存の全体像

### 最重要ポイント：2つの独立したID体系が存在し、互いに紐付いていない

| ID | 何の識別子か | どこで発行される | どこに保存されるか | サーバーへ送られるか |
|---|---|---|---|---|
| **playerId** | 端末内の「複数プレイヤー」機能の主キー（`js/playerProfile.js`） | `crypto.randomUUID()`（最初のプレイヤーは固定値`"default"`） | `localStorage`（`equalLoveIntroQuiz.players`） | **送られない**（完全ローカル） |
| **Firebase匿名認証UID** | オンライン機能（対戦・ランキング・公開プロフィール）の主キー | `signInAnonymously()`（初回起動時に自動） | ブラウザには見えない場所（Firebase Auth SDKが自前のIndexedDBで管理） | Realtime Databaseの各パスのキーとして使われる |

**この2つの間に対応表は存在しません。** つまり「このプレイヤーのクラウドデータはどれか」をアプリ自身も把握できていない状態です。さらに重要な点として、

> **Firebase匿名認証は、ブラウザのサイトデータを削除すると同じUIDに二度と戻れません。** 次回開いたときは完全な別人として新しいUIDが発行されます。メール・パスワード・Google/Appleログインなどの「本人確認の手段」が一切無いため、今の設計のままでは「同じユーザーとして自動復元する」という理想は原理的に実現できません。

これが、バックアップ設計全体の一番の壁になります（詳しくは④⑤で説明します）。

### 保存場所ごとの分類

#### IndexedDB（4つの独立DB、いずれも端末グローバル＝全プレイヤー共通、著作権コンテンツ）

| DB名 | 内容 | モジュール |
|---|---|---|
| `equalLoveIntroQuizAudio` | 曲の音源ファイル本体 | `js/audioStorage.js` |
| `equalLoveIntroQuizLyrics` | 歌詞本文＋タイミング | `js/lyricsStorage.js` |
| `equalLoveIntroQuizCalls` | ライブコールのタイミングデータ | `js/callStorage.js` |
| `equalLoveIntroQuizCallGuide` | コールガイド（口上の練習本文） | `js/callGuideStorage.js` |

これらは「データパックを再取得すればよい」種類のコンテンツで、個人のプレイ実績ではありません。callData/callGuideDataには既に手動のJSON書き出し機能がありますが、audio/lyricsには全曲一括エクスポート機能がありません。

#### localStorage（プレイヤーごとに分離、`equalLoveIntroQuiz.{接頭辞}...`）— **バックアップの主対象**

| データ | キー | モジュール |
|---|---|---|

| 通常イントロクイズのハイスコア | `highScore.{出題数}.{カテゴリ}` | `js/highscore.js` |
| 通常イントロクイズの履歴（最大100件、曲別正誤内訳含む） | `playHistory` | `js/history.js` |
| その他全モードの統一履歴（最大200件） | `unifiedPlayHistory` | `js/playHistory.js` |
| タイムアタック履歴（問題別正誤・選択内容まで） | `timeAttackHistory` | `js/timeAttackHistory.js` |
| 苦手曲判定用の曲別累計（イントロ/タイムアタック/ランダム再生） | `weakSongStats` | `js/weakSongStats.js` |
| 苦手曲判定用（歌詞クイズ専用） | `lyricsQuizWeakSongStats` | `js/lyricsQuizWeakSongStats.js` |
| 各モードの自己ベスト（合計タイム・平均回答時間等） | `normalQuizTimeBest.*` / `timeAttackBest.*` / `timeAttackBestReach.*` / `randomPlaybackBest.*` / `randomPlaybackBestReach.*` / `lyricsQuizBest.*` | `js/normalQuizTimeScore.js` 等6ファイル |
| ランキング参加条件を満たした自己ベスト（Firebase送信元データ） | `rankingCandidateBest` | `js/rankingCandidateStore.js` |
| 推しメン・最推し | `oshiMembers` | `js/oshiMembers.js` |
| お気に入り曲 | `favoriteSongs` | `js/favoriteSongs.js` |
| 自作プレイリスト | `playlists` | `js/playlists.js` |
| 「みんなのプロフィール」公開設定 | `publicProfile.enabled` | `js/publicProfilePayloads.js` |
| 旧バージョンの称号進捗（読み取り専用で保持） | `titles.perfect.*` / `titles.equalLoveKaiden` | `js/achievementProgress.js`内`readLegacyFlag` |

#### localStorage（端末グローバル＝プレイヤー非依存）

| データ | キー | モジュール |
|---|---|---|
| プレイヤー一覧 | `players` | `js/playerProfile.js` |
| 現在選択中のプレイヤー | `activePlayerId` | `js/playerProfile.js` |
| **オリジナル問題作成モードのプリセット** | `customQuizPresets` | `js/customQuizPresets.js` |
| 各種サウンド設定 | `sfxEnabled` 等5キー | `js/soundManager.js` |
| 歌詞表示モード等の表示設定 | 数キー | `js/lyricsSync.js` 等 |

> ⚠️ **見つかった不整合**：`customQuizPresets`（オリジナル問題作成モードのプリセット）だけが、他のゲームデータと違って「プレイヤーごとに分かれていない」設計になっています。複数プレイヤー運用時、全プレイヤーで共有される状態です。意図した設計かどうか本人に確認が必要です。

#### sessionStorage（タブ/セッションを閉じると自動消滅）

PWA更新直後のバナー表示・お祝いポップアップの既読・お知らせの「あとで」フラグのみ。恒久データではないため、バックアップ対象外で問題ありません。

#### `js/storagePersistence.js`（ブラウザの「永続ストレージ」許可API）

`navigator.storage.persist()`を呼び、許可されれば「端末の空き容量不足時にブラウザが自動で消す」対象から除外されます。**ただしこれは"自動削除"だけの対策であり、ユーザー自身がサイトデータを手動削除する操作に対しては一切効果がありません。** また、バックアップ／復元の仕組みはこのファイルにも他のどこにも実装されていません。

## ②消える可能性があるデータ一覧（操作別）

ブラウザ・OSによって挙動が完全には断定できないものは、その旨を明記します。

| 操作 | 影響 |
|---|---|
| 普通にタブを閉じる | **何も消えない**（sessionStorageの一時データのみ消えるが、元々恒久データではない） |
| PWAを終了する（ホームボタン等） | **何も消えない** |
| 閲覧履歴だけ削除する | 通常は影響なし。ただしブラウザの「詳細設定」次第でサイトデータも含めて消す設定にしている場合は消える（**断定不可**） |
| キャッシュを削除する | Service Workerが持つ「アプリ本体（HTML/JS/CSS）」のキャッシュは消えるが再取得されるだけで実害なし。IndexedDB/localStorageは通常別区分のため残る可能性が高いが、ブラウザ・OSバージョンにより「キャッシュ」の範囲定義が異なるため**完全には断定不可** |
| Cookie/サイトデータを削除する | **称号・履歴・自己ベスト・お気に入り・設定・音源・歌詞など、ほぼ全データが消える。** Firebase匿名認証のセッションも消え、次回は新しいUIDになる |
| サイトストレージを消去する（Android Chrome等） | 上記と同じ、**全データが消える** |
| PWAをホーム画面から削除する | 多くの場合、そのオリジンの全データ（＝上記と同じ範囲）が消える可能性が高い。iOS/Androidでの実装差があり**完全には断定不可** |
| Chrome/Safari側のデータを削除する | 上記と同じ範囲 |
| 端末を変更する | 新しい端末には何も引き継がれない（ローカルデータもFirebase匿名認証も別物として始まる） |
| PWAを再インストールする | 削除後の再インストールであれば、削除時点で上記と同じ範囲が消えている |

**要するに、「サイトデータの削除」に類する操作1つで、称号・プレイ履歴・自己ベスト・お気に入り・設定など、大切なデータのほぼ全てが一度に失われる状態です。**

## ③現在すでにクラウド保存されているデータ一覧

結論から言うと、**「個人データの復元用バックアップ」として使えるものは、現状ひとつも存在しません。**

| Firebaseパス | 内容 | 制約 |
|---|---|---|
| `publicProfiles/{uid}` | 表示名・推し・**取得済み称号IDの一覧のみ**（取得日等は含まない）・複合称号3種のフラグ | 「みんなのプロフィール」公開をONにした人だけ。**OFFにすると削除される**（バックアップとして機能しない設計） |
| `timeAttackLeaderboardsV3/...` | タイムアタックの自己ベストタイム（**ノーミスクリアの回だけ**、組み合わせごとに1件） | 公開設定ONの人だけ。履歴・ミスありの記録・他モードの自己ベストは含まれない |
| `rooms/{roomId}` | オンライン対戦の進行中データ | 対戦終了・退出で削除される、**完全に一時的なデータ** |

いずれも「本人確認の手段がない匿名認証UIDに紐づく」ため、端末が消えた場合に同じユーザーとして辿り着く手段自体がありません（③のデータそのものは残っていても、迷子になります）。

## ④改善が必要な部分

1. **本人確認の手段が無い**：匿名認証のままでは「同じユーザー」を再認識できない。これが最大の課題。
2. **playerIdとFirebase UIDが紐付いていない**：複数プレイヤー機能と、クラウド機能が別々の世界になっている。
3. **公開プロフィールは「OFFで削除」される設計**：バックアップ用途と、公開/非公開の切り替えが同じ仕組みに乗っており、目的が競合している。
4. **称号は「今解放されているID」のみ**：取得日時・進捗カウンターなど、復元に必要な情報が送られていない。
5. **履歴・自己ベスト・苦手曲・お気に入り・プレイリスト・カスタム問題は一切クラウドに存在しない。**
6. **セキュリティルールがリポジトリで管理されていない**：`docs/HANDOFF.md`に本人自身が「現時点で本番に反映されているルールの正確な全文は、コードからは完全には確認できていない」と明記しており、Firebase Consoleでの手動変更の積み重ねで、今どんなルールが本番にあるか誰も正確に把握できていない状態です。バックアップ機能を安全に作るには、まずここを直す必要があります。
7. `customQuizPresets`のプレイヤー非依存という不整合（①参照）。

## ⑤推奨するバックアップ・復元設計（提案・まだ実装しません）

### 本人確認の手段（最重要の決定事項）

以下のいずれか、または組み合わせが必要です。それぞれのメリット・デメリットを提示します。

| 方式 | メリット | デメリット |
|---|---|---|
| **A. 匿名認証のまま「復旧コード」方式**（アプリが表示するコードを本人がスクショ・メモしておき、新端末でそのコードを入力して復元） | 実装が比較的軽い、既存の匿名認証の仕組みを流用できる、メール等の個人情報が不要 | ユーザーがコードを保存し忘れると復元不可能。「事前に備えないと復元できない」点は自動復元の理想から少し外れる |
| **B. Googleサインイン等へアップグレード**（Firebaseの「匿名アカウントのリンク」機能で、今の匿名UIDはそのままに、Googleアカウント等を後付けで紐付ける） | 一度リンクすれば、同じGoogleアカウントでログインするだけで自動的に元のUIDへ戻れる。ユーザーが何かをメモする必要がない | 実装がやや複雑、Googleアカウントを持たない・使いたくないユーザーへの配慮が必要、UIに「ログイン」という新しい概念が増える |
| **C. 何もしない（現状維持）** | 実装コスト0 | 今回の目標（機種変更等でも復元できる）を達成できない |

**個人的な意見としては、まずはA（復旧コード）を最小構成として用意し、余裕があればB（Googleログイン等）を任意のオプションとして追加する、という段階導入が現実的**だと思います。決定は本人にお任せします。

### バックアップの単位・タイミング

- バックアップの単位は「1プレイヤー分」（`playerId`ごと）にすべきです。今のクラウド機能（uid単位）とは粒度を合わせ直す必要があります。
- 自動同期のタイミング案：称号解放時・クイズ完了時・自己ベスト更新時・プロフィール変更時など「重要な変化があった直後」に、軽いデバウンス（連続更新をまとめて1回にする）をかけて送信。既存の`publicProfileSync.js`と同じ「失敗してもプレイ自体はブロックしない」方針を踏襲。
- 保存先は既存のRealtime Databaseで十分（新しいFirebaseプロダクトを増やす必要はない）。

### バージョン管理・上書き事故の防止

- 各バックアップに`updatedAt`（サーバー時刻）を必ず持たせ、復元時は「クラウド側が明らかに古い場合は復元しない」といった安全策を入れる。
- 「クラウドのデータでローカルを上書きする」のは、**ローカルにそのプレイヤーのデータが実質存在しない場合（初回・データ消失後）だけ**に限定する。通常プレイ中は常にローカル→クラウドの一方向を維持し、逆方向の上書きは初回同期・復元操作の時だけに絞ることで、事故の可能性を構造的に減らせます。

## ⑥既存ユーザーを安全に移行する方法

1. 新しいバックアップ機能を配信した瞬間は、**まだ誰のクラウドにも何もデータが無い状態**です。
2. 各ユーザーが次にアプリを開いたとき、「今ローカルにあるデータを、初めてクラウドへアップロードする」だけの一方向処理を1回だけ行う（読み込みは一切行わない）。
3. アップロードが成功したことを確認できたら、以後は通常の自動バックアップへ移行する。
4. **この移行処理は、既存のローカルデータを一切書き換えません。** 「クラウドが空だからローカルの内容で埋める」だけの操作なので、今持っている称号・履歴・自己ベストが初期化されるリスクはありません。
5. 万が一、同じ`playerId`に対してクラウド側に既にデータがある状態（想定外のケース）に遭遇した場合は、自動で上書きせず「新しい方を残す」または「復元確認をユーザーに委ねる」といった安全側の分岐にする。

## ⑦管理者による復旧機能をどう実現するか

このアプリには既に`js/adminConfig.js`という前例があります（`ADMIN_UID`という1人分のUIDをハードコードし、UI側でそのUIDと一致する場合だけ管理者用ボタンを表示、実際の権限はFirebase Security Rules側で担保する、という設計）。これと同じ考え方を踏襲するのが自然です。

- **フロント側に管理者用パスワードを直接書き込むような方式は使いません**（本人の懸念どおり、それは簡単に突破される偽のセキュリティです）。
- 管理者判定は「今ログイン中のUIDが`ADMIN_UID`と一致するか」で行い、**本当の権限チェックは必ずFirebase Security Rules側**で行う（UI側のチェックは誤操作防止のための二重チェックに過ぎない、という既存方針をそのまま踏襲）。
- 「復元・書き換え」は「削除」より一段階危険な操作（データの中身を勝手に決めて書き込むため）なので、既存の削除限定ルールよりも慎重な設計が必要です。案としては：
  - 復元操作を行うたびに「いつ・誰が・どのユーザーの・何のデータを」変更したかのログを別途Firebase上に残す
  - 復元は「過去のバックアップの中から選んで書き戻す」だけに限定し、管理者が数値を自由入力できるような汎用編集機能は作らない（事故・誤操作のリスクを減らすため）

## ⑧セキュリティ上の注意

- 上記の通り、フロント側の判定はあくまで「見た目」であり、実際のアクセス制御はFirebase Security Rulesで行う必要があります。
- 現状、**本番のセキュリティルールがリポジトリで管理されておらず、正確な内容を本人も完全には把握できていない**ことが`docs/HANDOFF.md`に記録されています。バックアップ機能を安全に導入する前提として、**まずルールをテキストファイルとして書き出し、リポジトリで管理する体制に変えることを強く推奨します**（今後何を変更したか追跡できるようにするため）。
- 既知の課題として、オンライン対戦の`rooms/{roomId}`では「ルームのホストが、technicalには他プレイヤーのデータを上書きできてしまう」というRealtime Database特有のルール継承の仕組み由来のギャップが過去に確認されています（友人内利用なら実害は小さいと判断され許容されていますが、バックアップ機能の設計時にも同種の落とし穴（「深い階層のルールが浅い階層のルールを覆せない」というRealtime Databaseの仕様）に注意が必要です）。
- 一般ユーザーが「自分以外のuid配下」に書き込めないよう、ルール側で`auth.uid === $uid`のような形の制限を必ず設けること（既存の`rooms/{roomId}/players/{uid}`と同じパターンが使えます）。

## ⑨Firebase等を使う場合の容量・料金への影響

- 現在の構成はRealtime Database（無料のSparkプラン想定）のみで、音源・歌詞などの大容量データはクラウドに置かない方針を維持しています。これは料金面でも正しい判断です（音声のような大容量バイナリをクラウド化すると、あっという間に無料枠を超える可能性があります）。
- 今回追加を検討しているデータ（称号ID・履歴サマリー・自己ベスト数値など）は**すべてテキスト・数値のみ**で、1ユーザーあたり数KB程度に収まる規模です。個人利用〜友人間程度の想定ユーザー数であれば、Sparkプラン（無料枠：保存容量1GB、月間ダウンロード量10GB程度）の範囲で十分に収まると考えられます。
- 「過去数世代のバックアップを残す」場合も、テキストデータである限り影響は軽微です。ただし無制限に世代を積み上げるのではなく、「直近3〜5世代」「直近30日分」のように上限を設け、古いものは自動的に削除する設計にすることを推奨します。
- 音源・歌詞・コールなどの「データパックで再取得できるもの」は、今回の方針どおりクラウド化しないことで、料金面のリスクを最小限に抑えられます。
